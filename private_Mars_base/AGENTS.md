# 《火星基地失控 72 小时》单人完成路线图

这份路线图按“会使用结构体和文件读写、独立完成、有一到两周”安排。第一周完成一份能提交的版本，第二周如果有余量，再补边界测试、修改报告和演练提交。

## 1. 作业目标与验收方式

用 C11 编写命令行程序 `mars_sim`。程序读取基地初始状态、事件序列和行动序列，模拟 1～72 个时间片。每轮采取的行动已经由文件给定，你负责判断它能否执行、更新基地状态，并在基地失败或全部时间片结束时写出结果。

教师会在 GCC/Linux 环境中从源码重新构建，更换输入文件，并逐行比对结果。验收入口如下。

```sh
make clean && make
./mars_sim --base base.txt --events events.txt --actions actions.txt --output result.txt
```

提交材料包括源文件、头文件、Makefile、README、公开测试和项目报告。正常结果必须写入 `--output` 指定的文件，恰好 12 行，字段名、顺序、大小写和空格都要与题面一致。非法输入应以非零状态退出，并避免留下半截正常结果。

| 评分项 | 占比 | 开发时留下的证据 |
| --- | ---: | --- |
| 核心功能 | 40% | 公开样例的逐轮手算表，以及全部 12 行的比对结果 |
| 代码质量与工程规范 | 20% | 清晰的模块接口、根目录的主程序源文件、可重新构建的 Makefile |
| 边界处理 | 15% | 可重跑的正常、边界和异常用例，每例都有预期结果 |
| 协作分工与过程记录 | 10% | 个人承担的模块，以及“我的判断 → AI 的建议 → 我的验证结果”记录 |
| 文档与报告质量 | 10% | README 的运行说明，报告中的设计思路、难点、测试结果与反思 |
| 创新与额外贡献 | 5% | 必做项稳定后，如有实际改进，记录改动前后的差异 |

## 2. 开工准备清单

- [ ] **补齐 Linux 编译环境。** 已核对本机有 WSL Ubuntu。Windows 侧有 MinGW GCC，Ubuntu 内有 `diff`，但检查时缺少 `gcc` 和 `make`。在 Ubuntu 中安装 `build-essential`，再运行 `gcc --version` 和 `make --version` 验证。
- [ ] **亲手推演一次公开样例。** 先只看任务书第 7 页，画出“轮次、事件后、行动后、结算后”四列。第 2 轮应能解释电力怎样从 80 变成 65、再变成 55。算完才翻到第 8 页核对，最终应有 `TIME 4`、`POWER 45`、`OXYGEN 47`、`SCORE 35`。有差异时圈出第一次不同的格子。
- [ ] **确定工程布局。** 按任务书第 9～10 页和评分表，把 `main.c`、其他主程序 `.c` 和 Makefile 放在工程根目录，测试放 `tests/`。Makefile 通过 `$(wildcard *.c)` 收集源文件，使用 `-std=c11 -Wall -Wextra -pedantic -O2`，构建命令以 Tab 缩进。根目录不要混入练习用的 `.c` 文件。README 给出与此布局一致的构建命令。
- [ ] **确认两个评分细节。** 任务书第 2 页写异常结果有“三行”，但格式定义与例子均只展示 `RESULT ERROR` 和 `REASON 具体错误原因` 两行。向老师确认是否按示例写两行，以及单人完成时“协作分工与过程记录”如何计分。答复前可先把错误输出集中在一个函数中，按示例设计；行动数与事件数不符应返回 `2`，这一项已写明。
- [ ] **隔离私人材料。** 个人路线图和草稿放在 `private_Mars_base/`。当前目录尚未初始化 Git；若日后启用，在第一次暂存前把 `/private_Mars_base/` 加入本地 `.git/info/exclude`。

## 3. 七天实施路线

| 时间 | 要完成的工作 | 用到的知识与考查的能力 | 当天如何验收 |
| --- | --- | --- | --- |
| 第 1 天 · 搭建工程 | 配好 Ubuntu，手算公开样例，编译第一个 `mars_sim`，接通四个命令行参数。 | 用 `argc/argv` 读参数，用 Makefile 构建，理解相对路径。练习让别人复现运行过程。 | `make clean && make` 成功。把三份输入放到另一目录，改变输出路径，程序仍能找到文件并写到指定位置。 |
| 第 2 天 · 初始状态 | 读取 `base.txt` 的六个字段，初始化一份共享的基地状态。 | 结构体、`fgets`、整数解析、范围检查。练习把文本转换为可信的数据。 | 字段换序仍可读取；重复、缺失、越界和 `12abc` 都能识别。初始资源、机器人、实验舱、故障与计数器均与题面相符。 |
| 第 3 天 · 事件与行动输入 | 把事件和行动读入数组。验证完整输入后，再进入仿真。 | 结构体数组、枚举、按行拆词。练习区分语法错误与执行条件不满足。 | 检查 `N` 为 1～72、每条事件有 1～3 对资源变化、`M=N` 且数量与有效行数一致。空行不计数。未知命令报错；合法的 `REPAIR SOLAR` 即使修不了，也应进入仿真。 |
| 第 4 天 · 跑通一个时间片 | 先用一个事件和 `WAIT` 走完一轮，再接入其余事件与故障。 | 指针传参、共享状态、状态更新顺序。练习定位第一次出现偏差的步骤。 | 固定顺序为**事件 → 行动 → 结算 → 截断 → 时间加一 → 判败并记录**。用手算表逐步核对。 |
| 第 5 天 · 完整仿真 | 补齐机器人、维修、重启、关闭实验舱，循环处理各轮并计算得分。 | 多条件判断、计数器、循环退出、整数除法。练习处理多条规则的相互影响。 | 用 `diff` 比对公开样例的全部 12 行。关闭实验舱当轮就省氧省水；成功重启通信扣电并清故障；成功执行 `REPAIR` 才增加 `REPAIRED`。 |
| 第 6 天 · 边界与异常 | 为正常流程、边界值和错误输入建立编号用例，检查结果文件和退出码。 | 等价类、边界值、预期结果和回归测试。练习用证据解释程序为何正确。 | 每个用例都有输入、预期输出或退出码、实际结果。至少有一例验证首轮失败后，第二轮不会执行。 |
| 第 7 天 · 提交演练 | 整理 README、过程记录和项目报告，在干净目录中模拟教师验收。 | 模块说明、可复现构建、技术复盘。练习向第一次看到工程的人解释设计。 | 只用待交材料就能重新编译并跑完公开测试。报告选一个真实难点，写明怎样发现、怎样修正、用哪条测试验证。 |

如果有第二周，先重跑开发中曾经失败的用例，再补遗漏的边界；最后按 README 从头操作一遍。完成这些之后，再决定是否有时间做一项能说明实际效果的改进。

## 4. 优先准备的测试

| 用例 | 怎么设计 | 预期结果 |
| --- | --- | --- |
| 同一轮换行动 | 初始氧气 2、水 1、舱体和温度安全，只输入一个 `DUST_STORM POWER 0` 事件。分别选择 `WAIT` 和 `SHUTDOWN LAB`。 | 前者氧气降到 0，在 `TIME 1` 失败；后者剩氧气 1、水 1，存活。用它检查行动、结算、判败的先后关系。 |
| 行动失败与输入错误 | 设 `ROBOT 0`，先执行 `ACTIVATE ROBOT`，再单独用未知行动名重跑。 | 前者增加 `FAILED_ACTION`，本轮照常结算；后者报告输入错误并非零退出。 |
| 维修电力刚好够 | 设置机器人已激活、有对应故障的场景，使行动前电力分别为 9 和 10。 | 电力 9 时维修失败，保留故障；电力 10 时成功，扣 10、清故障并累计维修次数。两次都应保留事件已造成的变化。 |
| 文件和数值边界 | 覆盖 `N=1`、`N=72`、`M!=N`、事件有四对资源变化、事件后舱体超过 100，以及结算后温度恰为 0 和低于 0。 | 数量不匹配返回 `2`；超出三对变化的记录报错；舱体回到 100；其他条件安全时，温度 0 可存活，负温触发失败。 |
| 提前结束与输出格式 | 设计首轮就失败、第二轮本可补回资源的输入；另外保存公开样例的完整预期输出。 | 首轮失败时 `TIME` 停在 1，后续资源没有加回。公开样例全部 12 行与标准结果一致，文件中没有调试内容。 |

**第一天的收工标准**：Ubuntu 能运行 GCC 和 Make；合上答案也能解释第 2 轮为什么剩 55 电力；给定 2 点氧气，能预测选 `WAIT` 或 `SHUTDOWN LAB` 会怎样改变这一轮的结局。
